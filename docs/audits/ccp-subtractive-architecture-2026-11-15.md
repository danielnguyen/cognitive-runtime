# CCP subtractive architecture audit — Cognitive Runtime

Assessment date: 2026-11-15. Scope: [CR issue #111](https://github.com/danielnguyen/cognitive-runtime/issues/111). This is an audit for independent review; it changes no executable behavior and authorizes no removal, migration, merge or deployment.

## Executive recommendation

Keep Cognitive Runtime (CR) as the runtime policy and turn-admission authority for the private Telegram companion. Keep Basic Memory Store (BMS) as the durable conversation/memory authority and Chat Orchestrator (CO) as the request, provider and presentation coordinator. Persistence in CR is necessary for restart continuity and authorization evidence; replacing it with process-local state would lose required behavior.

The clearest CR/CO subtraction opportunity is duplicated timing-contract maintenance: three policy tables and a coherence validator are identical at the inspected revisions. Consolidating their definition could reduce drift, but both HTTP boundaries must still validate inputs. The first user-visible simplification priority is preventing unnecessary evidence acquisition for ordinary questions; recent CR changes already address a concrete case, so preserve and qualify them before constructing another router. The largest confirmed duplicate chat pipeline is in BMS, not CR. Reconcile its retirement with the sibling audit before reorganizing CR locally.

Do not turn `runtime_state.py` or `models.py` length into a removal target. Their contents include atomic admission, owner/surface binding, stale-decision rejection and recovery. No verified off-the-shelf replacement for those combined contracts was established. Native SQLite transactions and Pydantic validation already provide important mechanics; retain those instead of adding a framework. Narrow compatibility and deferred surfaces only after checking consumers and retained data. There is no measured LOC saving, latency saving or total operating-cost reduction in this report.

## Actual request path and ownership

```text
Private Telegram adapter (contract / historical observation; live configuration unknown)
  -> CO authenticated POST /v1/chat -> orchestrate_chat
       -> BMS owner-scoped permission + durable conversation/lifecycle lookup
       -> CR thread selection/admission, session and exact turn binding
       -> CR governance/containment/presence/timing and other configured policy
       -> BMS scoped retrieval; CO assembles bounded provider context
       -> CO LiteLLM call and output/privacy handling
       -> BMS exact assistant message, trace and optional claim/support records
       -> CR completion and bounded message/continuation provenance
  <- CO response with durable conversation_id -> adapter delivery
```

This is a boundary map, not a claim that every optional step runs on every request. CO has early failure, clarification, pause and non-executing paths. No adapter-source or deployed-topology inference is made.

### Flags and operating dependencies

[CO settings][C-settings] 16–110 default runtime URL to absent and runtime overlays, companion, interaction governance, containment, restraint, hygiene, privacy, capability registry, strict world/relationship/capability paths, claim capture, evidence acquisition, history follow-up and DSA to false. Dependency validation at 149–216 rejects selected inconsistent combinations. Defaults are not deployed values.

World-state and relationship reads are nevertheless called on the ordinary runtime-configured path: CO `_resolve_world_state` (5843), `_resolve_relationship_context` (6055), and calls at 11944/11970. Their **strict** flags choose stronger authority handling; false does not demonstrate that the entire subsystem is unused. Likewise, unconditionally registered CR routes are not proof of actual consumers.

CR source pins FastAPI 0.115.6, Pydantic 2.10.5, PyYAML 6.0.2 and Uvicorn 0.34.0 in `api/requirements.txt`; its Dockerfile uses Python 3.12. SQLite is Python's standard-library database interface. `RUNTIME_STATE_DB_PATH` defaults to `./data/runtime_state.sqlite3`; `COMPANION_CONTRACTS_DB_PATH` defaults locally to `./data/companion_contracts.sqlite3`, with the image setting `/data/companion_contracts.sqlite3`. The runtime path is not explicitly set by that Dockerfile: verify the deployed path and persistent mount before any durability conclusion. `TRUSTED_WORLD_STATE_VERIFIERS_PATH` is optional; missing configuration leaves no trusted verifiers, while invalid configuration fails closed. `SQLITE_TRANSACTION_TIMING_ENABLED` is server-only and default off.

CR `api/main.py` has no application API-key dependency analogous to CO's `require_api_key`. Payload owner fields and internal binding checks do not authenticate an external caller. The trust boundary therefore needs verified restricted service access in deployment; this audit cannot certify it. Do not expose CR directly, or describe schema validation as authentication, during any later simplification.

## Native alternatives checked

Checked on 2026-11-15 against primary documentation and pinned source:

- [SQLite transactions](https://www.sqlite.org/lang_transaction.html) provide one concurrent writer and explicit immediate transactions. CR already uses this primitive. It serializes database work, not cross-service publication or owner permission; retaining application checks is necessary.
- [Python 3.12 sqlite3](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.set_trace_callback) supports native context-manager transaction handling and a statement trace callback. The callback is not evidence of equivalent commit/rollback duration measurement. The diagnostics replacement remains unverified.
- [Pydantic 2.10 JSON Schema](https://docs.pydantic.dev/2.10/concepts/json_schema/) and [validators](https://docs.pydantic.dev/2.10/concepts/validators/) provide schema generation and field/model validation. The repository already uses them. A generated client has not been demonstrated to preserve the timing validator's cross-field semantics or authorization provenance; do not delete those checks on the strength of schema support alone.

A shared contract package, BMS-backed CR projection, generic checkpointer, external policy engine, or whole-service replacement remains a hypothesis. None has been installed, benchmarked or qualified here. The competitive assessment's feature comparisons are historical decision context, not current replacement certification. This audit recommends no new dependency.

## Cross-service reconciliation and lowest-risk sequence

[BMS audit #71](https://github.com/danielnguyen/basic-memory-store/issues/71) now has [draft PR #72][B-audit]; [CO audit #240](https://github.com/danielnguyen/chat-orchestrator/issues/240) had no matching audit PR when checked. The BMS draft agrees that canonical records, policy enforcement and exact publication should remain, and identifies direct chat and initiative ownership as subtraction candidates. Its findings remain subject to independent review.

BMS `main._run_chat` and both chat endpoints (1627–1950) still perform a separate orchestration path; CO's normal orchestration uses BMS conversation/retrieval/message APIs. The [older technical-debt record][P-debt] anticipated this duplication. Retiring that path could remove an entire competing lifecycle; splitting CR's large files cannot. External callers remain unknown, so this is not a declaration that BMS chat is safe to delete.

The BMS audit also identifies overlap in initiative decisions. CR restraint/presence and BMS durable preferences are complementary, and CO reads proactive preferences in its presence resolver. They are not proof that CR already implements every BMS event evaluator. Before any transfer, select only the MVP's opted-in watch behavior and preserve cooldown, consent, expiry and feedback. Do not move the whole evaluator or add another scheduler. DSA is only an upstream source dependency in the observed CO contract; its implementation was not inspected and no replacement conclusion depends on it.

1. Obtain independent review of all three reports and reconcile decisions in Projects, the designated consolidated decision record. No consolidated file or Projects write is created here.
2. Resolve actual caller/flag uncertainty from existing scoped configuration and redacted route-level evidence, without private payloads. Verify CR service isolation and persistent paths; source defaults are insufficient. Keep unavailable observations UNKNOWN.
3. Qualify the existing ordinary-question evidence guard. Measure whether unnecessary probes/refusals remain before proposing another mechanism.
4. If separately authorized, compare one timing-contract consolidation against its versioning/build costs; retain producer and consumer validation. Independently review both service changes.
5. Retire compatibility endpoints only after migration evidence. Keep this separate from policy or storage changes so rollback is straightforward.
6. Consider world/relationship storage or multi-persona narrowing only after consumer, data-lifecycle and recovery evidence. Any architectural migration needs a new bounded decision; no destructive subtraction is justified now.
